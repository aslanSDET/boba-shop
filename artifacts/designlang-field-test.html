Field test 31 August 2026 designlang 12.21.0

The colours are real.
The analysis is not.

I pointed designlang at two food brands with opposite design languages and read every file it produced. Palette extraction is genuinely good and directly usable. Four of the five analysis layers assert conclusions their own numbers contradict — with the receipts below.

The receipts

Every claim below is checkable against the files in research/designlang/. Expand any row to see the raw output.

1 · Semantic roles ignore the usage counts in the same fileoatly-com-DESIGN.md 
| role      | hex       | usage |
| primary   | `#f8c8d8` |   4   |
| secondary | `#fdcf85` |   7   |
| accent    | `#98c5d3` |   1   |
The problem: “primary” appears less often than “secondary”, and “accent” was promoted to a semantic role on a single occurrence. The tool reports the counts that disprove its own role assignment, in the same table.
2 · visual-dna contradicts design-tokens from the same runsweetgreen · both files 
// sweetgreen-com-visual-dna.json
"materialLanguage": {
  "label": "material-you", "confidence": 0.45,
  "signals": [{ "detail": "pill shapes + soft shadows" }],
  "metrics": {
    "shadowProfile": "soft",
    "avgShadowBlur": 0,
    "maxShadowBlur": 0
  }
}

// sweetgreen-com-design-tokens.json — same run, same page
"shadow": {
  "sh0": { "$value": "rgba(0,0,0,0.4) 0px 0px 3px 0px" },
  "sh1": { "$value": "rgb(199,197,199) -3px -3px 5px -2px" }
}
The problem: the classifier justifies “material-you” with soft shadows while its own blur metrics read zero — and the token extractor, on the same page, found real 3px and 5px shadows. "soft" is a default string, not a measurement.
3 · A classification shipped at confidence zero with no evidenceoatly-com-visual-dna.json 
"materialLanguage": {
  "label": "flat",
  "confidence": 0,
  "signals": [],
  "metrics": { "avgRadius": 2538, "maxRadius": 9999, "hasPill": true }
}
The problem: a label with zero confidence and an empty signals array is not a finding, but it is emitted in the same shape as a real one — and downstream files quote it as fact. Separately, avgRadius: 2538 comes from averaging in the 9999px pill idiom, which makes the mean meaningless.
4 · The type scale has one role, and it is wrong*-design-tokens.json 
// sweetgreen — "semantic.typography"
"body": { "$value": {
  "fontFamily": "SweetSansText",
  "fontSize":   "80px",
  "lineHeight": "68px",
  "fontWeight": "400"
}}

// oatly
"body": { "$value": {
  "fontFamily": "Margo Pro Regular",
  "fontSize":   "32px",
  "fontWeight": "700"
}}
The problem: 80px with a 68px line-height is a hero headline, not body text. Both sites got their most prominent type mislabelled as body, and there is exactly one typography role — so there is no scale at all.
5 · Fonts are named but unusableprimitive.fontFamily 
sweetgreen → SweetSansText, SweetSans, Grenette, Times
oatly      → Margo Pro Regular, Margo Pro Bold, oatly-icons
The problem: every one is a licensed custom face. The tool reports the name and offers no substitute, no classification, and no metric you could match against. The typography half of “inspiration in” arrives dead.
6 · Spacing is measurements, not a scaleprimitive.spacing 
sweetgreen → [1, 23, 28, 35, 40, 48, 54, 60, 70, 98]
oatly      → [1, 15, 24, 30, 40, 44, ...]
The problem: 23px and 35px are observations, not system values. No 4pt or 8pt grid is inferred, so you cannot build against this — you would be reproducing one page's rounding errors.
7 · Tailwind ramps are 10 parts invention to 1 part measurementoatly-com-tailwind-v4.css 
--color-primary:     #f8c8d8   /* measured — Oatly's soft pink */
--color-primary-500: hsl(340 77% 50%)  /* invented — hot pink */
--color-primary-900: hsl(340 77% 16%)  /* invented — maroon */
The problem: the 50–950 ramp holds hue and saturation fixed and walks lightness, so every step but one is a colour Oatly has never used. Perceptually it is not even an even ramp. Take --color-primary; discard the rest.
8 · Both runs exit non-zero after succeedingstderr 
✓ ...-form-states.json (302B) — Forms + States
✖ Extraction failed

  The "string" argument must be of type string or an
  instance of Buffer or ArrayBuffer. Received undefined
The problem: the crash lands after every emitter has finished, so the output is complete and the failure is cosmetic — but a tool that returns 1 on success cannot be scripted or put behind a CI gate without wrapping it.

The split

Worth using

Colour, and only colour

  • Palette read off the live DOM, correct on both brands
  • Usage counts tell you which colours actually carry the page
  • *-shadcn-theme.css is paste-ready into globals.css
  • Neutrals are separated from brand colours, which most extractors miss
  • --radius is a single measured value and is believable
Ignore

Every layer above colour

  • Type scale — one role, and it captured a headline
  • Font families — proprietary, no substitutes offered
  • Spacing — raw pixels, no grid inferred
  • visual-dna — contradicts the token file beside it
  • voice.json — “verbs” include your, salads, sides
  • Tailwind colour ramps — synthetic around one real value

What this changes

In the landscape survey I called designlang “the single best inspiration-in primitive” and the concrete artefact every other layer builds on. Hands-on, that is too generous. It is a very good colour picker with six unreliable features stacked on top, and the unreliable ones are not marked as such in the output — which is worse than not shipping them, because a coding agent reading DESIGN.md will quote material-you and body: 80px straight into your CSS.
