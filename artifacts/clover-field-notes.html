How to read this

Two standards of proof are mixed together here, so every finding is tagged with which one it meets.

Confirmed means verified against Clover's own documentation or measured by our own sandbox spike. Claimed means a specific, falsifiable statement in someone else's production code — usually with the scar tissue to match. Plausible, and not yet verified by us.

Nothing from these repos has been copied into our code, and nothing should be. Almost all of it is unlicensed. The clones live at NodeProjects/clover-reference/, deliberately outside our public repo, with a per-repo map in their own README.md.

The search technique matters more than the results

The three repos closest to our situation are invisible to GitHub repo search — not one of them mentions Clover in its name or description. All three were found by code-searching for CLOVER_MERCHANT_ID.

Search for the environment variable, not the product. Note also that “clover” is a badly polluted keyword: the bootloader, Cloverly the carbon company, Naver Clova, and several game mods crowd every result page. A number of hits for scl.clover.com are card-testing fraud tooling; those were not opened.

The three that match our situation

One independent developer, one real bricks-and-mortar business, Clover end to end. This is the genre we were looking for.

chiang-mai-ai-phone-ordering

Django · a Thai restaurant

30 commits · pushed 26 Aug 2026 · unlicensed · found via CLOVER_MERCHANT_ID

The closest match to our architecture, and they got there without ever seeing our plan. Their migration added clover_item_id, clover_modifiers, clover_order_id, clover_pushed and clover_error in one go — which is PLAN.md §6, written by a stranger. That is the most reassuring single thing in this survey.

Borrow

  • Sync preserves locally-curated fields, matched by name. Clover owns names, prices and modifiers; their phonetic aliases and Thai names survive a resync. We hit this the moment we add a photo, description or tag that Clover has no field for.
  • An item that vanishes from Clover is marked unavailable, not deleted — to keep that curation and the order history intact.
  • A manual re-push command taking a local order id, with --force. For a two-store shop that beats an automatic retry queue.
  • A --dry-run flag on the sync. Ours should have one.
  • The push never raises to the caller: “the local order + SMS are the source of truth / backup”.

sanqinMVP

NestJS + Prisma · a restaurant site

561 commits · pushed 28 Aug 2026 · unlicensed

We already knew Hosted Checkout has no calculation engine and silently ignores taxRates, so we must compute the total ourselves. The open question was how to do that without trusting the browser with the number. This repo answers it in about sixty lines.

Borrow

  • The signed pricing token. The server computes the total, then issues an HMAC-signed token binding totalCents + a cart fingerprint + the checkout intent id, with a 15-minute expiry. The browser carries the price and cannot alter it; the server verifies signature, fingerprint and amount before charging.
  • Recalculate, never trust, amounts that come back in checkout metadata — the same conclusion our own findings.md reached.
  • The provider-adapter split, if we ever add a second processor. We will not soon; noted so we don't build it prematurely.

Wrong domain, right hard-won knowledge.

puneet

Next.js · a healthcare boarding facility

1,456 commits since Nov 2025 · pushed 28 Aug 2026 · unlicensed · zero stars, unknown author

The most valuable repo in this survey, and the one we should copy the least from. The domain is wrong — pet boarding, card-present countertop terminals — and the code is unlicensed. Its value is that the author documented every Clover bug they shipped and reverted, in a debt map and in a long comment banner at the head of every file.

Clover's documented behaviour and its actual behaviour differ in ways that are individually small and collectively expensive, and the failures are quiet — a null, a wrong status code, a missing row.

That is from a section titled “Fifteen defects, and all but one were found by running the code.” Six of the fifteen were already committed and described as working. It is the same shape as our own tax-divisor episode: inferred from the docs, wrong by a factor of ten, caught only because we ran an order and read the total back.

Borrow — patterns, never code

  • “A sale that succeeded with no paper is a nuisance. A sale reported as failed because a second request failed is a double charge.” Every call that is not the one moving money returns null rather than throwing, with a short timeout and no retries. This is the right shape for our order-push and ticket-fire steps.
  • A webhook delivery is a hint, never a fact. Record that Clover mentioned an object id, then re-read that object from the API with the merchant's own token. Every decision comes from the read.
  • Open the intent row before calling Clover, carrying the idempotency key you are about to send. A mid-charge crash is then both reconcilable and safe to retry.
  • A sweep as the backup for the webhook that never came. Theirs runs every 15 minutes.
  • Reconcile the gap, not the event. Ask “does our ledger account for everything Clover has reversed”, write only the shortfall, one row per reversal keyed to its own Clover id. That is what makes it safe to run twice.
  • Never report a capability as working if you cannot prove it. They report charge as untested forever, because taking a payment cannot be proven without taking one.
  • An unattached-payments queue — real money Clover took that the app cannot place, held for review rather than discarded. Exactly the failure our own Hosted Checkout finding implies.

Do not borrow

  • Their auth. They migrated Clerk → WorkOS for org-model reasons that are not ours; our Clerk decision stands.
  • Anything from their card-present terminal path. We are online-only.

mbates-clover

TypeScript client library

16 commits · pushed 23 Jul 2026 · MIT — the only permissively licensed repo here

Covers charges, refunds and customers. Not orders, inventory or line items — which is most of what we need. Read it; do not adopt it.

Borrow

  • The two-host split stated cleanly: scl* for Stripe-shaped ecommerce /v1/…, api* for platform /v3/merchants/{mId}/….
  • A typed error hierarchy behind one parseCloverError.
  • Defaulting an idempotency-key header on every mutating call.
  • WebCrypto webhook verification, so it runs on edge runtimes rather than Node only.

clover-online-orders

Zaytech's “Smart Online Order for Clover”

135 commits · last 17 Jun 2023 · commercial plugin, “License: Clover app”

Not Clover's, and not the mirror-owner's. A personal mirror by an individual developer of a commercial WordPress plugin sold in Clover's marketplace, originally written in 2016. It is the closest commercial analog to what we are building.

Borrow — as a checklist, not as code

  • Confirmation that the middleware tier is not optional. It never calls Clover. Every request goes to their own hosted API. Nobody puts Clover credentials in a browser — our Amplify Functions are the same shape as their API tier.
  • They built their own customer accounts — login, signup, SMS phone verification — rather than using anything of Clover's. Direct precedent for our Clerk decision.
  • What a finished Clover storefront needs beyond a menu, visible in their API surface: opening hours, opening status, blackout dates, order types, stock tracking, item stocks, order removal, merchant notification. Clover already knows all of it and we have not planned to read any of it.

export-api-examples

Clover's own bulk data export (beta)

Last touched 2019 — treat every detail as needing re-checking

Relevant only if the marketing engine ever wants order history in bulk rather than page by page. The constraints are unusual enough to be worth knowing before you design around it.

Borrow — the constraints

  • Service is only up US 10:00–15:00 UTC; outside that it returns 503 with the available hours. Sandbox has no time limit.
  • 1,000 objects per file, files deleted after 24 hours, maximum 30-day range per request.
  • Only a few concurrent exports before it 503s — you must wait for each to finish.
  • Aimed at “merchants that have installed your app”, so it may require an app rather than merchant tokens. Unverified

Every finding

Grouped by what it touches. The evidence column is the whole point — treat Claimed rows as leads to test, not facts to build on.

Webhooks

FindingDetailEvidenceSource
Two webhook systems, different auth Platform/merchant sends X-Clover-Auth, a static UUID with no signature, timestamp or replay protection. Hosted Checkout sends Clover-Signature: t=…,v1=…, HMAC-SHA256 over ${t}.${rawBody}. Our PLAN.md says “signature verification” as if there were one thing. ConfirmedClover docs
A delivery is a hint, never a fact Record that Clover mentioned an object id, then re-read it from the API with the merchant's token. On the platform webhook this is not optional — possession of a static UUID is the entire proof of origin. Claimedpuneet
Non-200 is retried forever A status code is a scheduling instruction, not an opinion. Record unprocessable events, close them with a reason, answer 200. Reserve non-200 for “I genuinely could not record this”. Claimedpuneet
The handshake cannot be authenticated Clover POSTs {"verificationCode": "…"} before the auth header starts appearing, so the first message can never carry the secret. Their fix: keep that branch live only while the secret env var is unset, so the door shuts as you finish walking through it. ConfirmedClover docs
A retry loop can spin for weeks Deliveries naming a superseded merchant retried every 15 minutes for 18 days — roughly 1,700 attempts — because the handler read with the current merchant's token, Clover cannot answer for another estate, and “unreadable” was skipped and left for next time. Claimedpuneet
Compare secrets in constant time timingSafeEqual throws on differing lengths, so the length check must come first. Claimedpuneet

Money and orders

FindingDetailEvidenceSource
Hosted Checkout has no refunds or voids Clover's own words: it is “a customer-facing payment interface, not a fully-featured payment system for merchants.” Every refund would happen by hand in the dashboard, and our side learns of it only by webhook or sweep. ConfirmedClover codelab
Hosted Checkout cannot use Clover inventory Stated in the same README. Confirms in writing what our spike measured: no inventory link, no calculation engine, taxRates silently ignored. ConfirmedClover codelab · our spike
POST /v1/orders/{id}/pay may link order to payment Ecommerce host, same clv_ token. Would let us create the order properly — inventory-linked, Clover applying its own tax — and then pay it. They could not verify it; their sandbox token had expired and Clover rotates refresh tokens. Our tokens can. Claimedpuneet
A reversal is not always a refund Calling /v1/refunds on a charge from the same batch produces a void: result: "VOIDED" with an empty refunds[]. Reconciling on refunds[] alone misses every same-day reversal and reports the money as still taken. For a boba shop, same-day reversal is the normal case. Claimedpuneet
A refund that omits its amount takes the whole charge Silent, and exactly the wrong direction to be wrong in. Claimedpuneet
/v1/orders/{id}/returns refunds the whole order …while echoing your requested amount back in the response. About as quiet as a money bug gets. Claimedpuneet
A tip makes /v1/refunds refuse a partial And Clover does not expose how a refund splits across subtotal, tax and tip — the refund element carries none of its own, and the nested payment holds the original's. Claimedpuneet
Money can arrive that you cannot place Clover takes payment and creates its own order; if our side crashed in between, nothing links it to a customer. They built a review queue and a nightly sweep for it. Claimedpuneet
Idempotency keys are honoured On retry with the same key, Clover returns the original charge rather than making a second one. Write the intent row before calling. Claimedpuneet · mbates
Compute server-side, sign the total HMAC token binding totalCents + cart fingerprint + intent id, 15-minute TTL. The client carries the price without being able to change it. ClaimedsanqinMVP
Tax rate unit is hundred-thousandths of a percent 6.25% is 625000. We inferred millionths from the docs, shipped it, and an order came back at $9.27 instead of $5.83. Confirmedour spike
Discounts apply before tax Measured on a live sandbox order. Confirmedour spike

Auth, permissions and platform behaviour

FindingDetailEvidenceSource
Permissions cannot be introspected Token exchange returns tokens and expiries and says nothing about permissions. They are ticked on the app in the developer dashboard and never reported back to the app holding the token. The only way to know is to provoke a refusal. Confirmedpuneet · our spike
…and the refusal code depends on the auth model On OAuth app tokens: 400 = permitted and rejected on merit, 403 = missing permission, 401 = dead token. On merchant-generated tokens we measured a missing permission as 401, and saw 403 only when an expand= value was rejected. Confirmedour spike
Clover rotates refresh tokens Two concurrent refreshes invalidate each other and take the connection offline. Claimedpuneet
A decline is HTTP 402 with no error.type Naive handlers return 500 for a perfectly ordinary declined card. Claimedpuneet
Clover rate-limits with 429 Three separate 429s were swallowed as nulls before anyone noticed. Claimedpuneet
externalPaymentId caps at 32 characters A UUID is 36. It truncates silently. If we key Clover payments by our own order id, it cannot be a raw UUID. Claimedpuneet
A clv_ token is single-use Splitting a payment across two cards means calling createToken() inside the loop, not once outside it. Claimedpuneet
The browser key tokenises and cannot charge Safe to expose — but gate the route that serves it anyway, because an open route tells anybody which businesses have a live merchant account. Claimedpuneet
Card-field mount() takes a CSS selector, not a node Passing the element fails the entire mount, with only a generic message. And React useId() yields :r1:, so a bare #:r1: is a selector syntax error — strip the punctuation. Claimedpuneet
There is no first-class Clover Node SDK Every integration surveyed hand-rolls fetch. Our dependency-free client is the normal answer, not a shortcut. Confirmedall nine

Printing and the kitchen

FindingDetailEvidenceSource
Nobody calls print_event. Not one of the nine. Including three real restaurants and a commercial ordering plugin. We are the only ones trying it. The others push an open order and let it land in the merchant's Orders app, with a second channel as the real backstop. Confirmedall nine
Our own print_event is unproven, not broken Route and permission are proven — it failed with “the default printing device is missing”, not “unauthorized”. Sandbox test merchants have no devices, so this only closes on the shop's real merchant. Confirmedour spike
POST /connect/v1/device/printers lists a device's printers Empty body. A merchant with an attached kitchen printer lists more than one; the first is the device's own roll. May answer our question without needing a sale — though still on the real merchant. Claimedpuneet
The print path is /print/text, not /print /v1/device/print answers 404 {"message":"Invalid URI"}. It cost a live terminal test to find, because the failure is invisible: the payment succeeds, the response says receiptPrinted: false, and the 404 appears only in the server log. (This is the REST Pay Display API — a different route from ours.) Claimedpuneet
X-Clover-Device-Id takes the serial Not the device id, despite the name. Claimedpuneet

The rule three codebases arrived at independently

A sale that succeeded with no paper is a nuisance. A sale reported as failed because a second request failed is a double charge.

So every call that is not the one moving money returns null rather than throwing, with a short timeout and no retries, and the caller is expected to be able to ignore the failure entirely. This is the correct shape for our order-push and ticket-fire steps, and it belongs in clover-ops.md as a rule.

What this changes

In rough order of how much they would move the design.

  1. Test POST /v1/orders/{orderId}/pay on the sandbox

    The one lead that would simplify the architecture rather than complicate it. If it works, we create a proper inventory-linked order and then pay it, which closes the tax-attribution gap without us owning a calculation engine. Roughly twenty minutes.

  2. Settle Hosted Checkout versus the tokenising iframe before Phase 2b

    Clover states refunds and voids are unavailable on Hosted Checkout, and a boba shop refunds wrong orders. Pizza62Sol shows both paths can run side by side, so this is a decision, not a fork. Re-check against current docs first — the codelab was archived in 2024.

  3. Printing is no longer a blocker

    The fallback — push the order, notify staff on a channel we control — is proven by three independent restaurants. Still worth asking the owner: when an online order arrives today, does paper come out, or does someone watch a screen?

  4. The webhook handler must dispatch on the merchant id in the delivery

    Billerica and Lowell are two merchant accounts with two credential sets. Reading with whichever token the handler happens to hold fails silently and retries forever — for eighteen days, in the one case we can see.

  5. Borrow the signed pricing token

    We already know we must compute the total. This is how to do it without trusting the client with the number, in about sixty lines.

  6. Catalog sync must preserve what Clover has no field for

    Photos, descriptions, tags. And an item that vanishes from Clover gets marked unavailable, not deleted.

  7. Put reconciliation on the roadmap, not in the surprises

    An unattached-payment queue and a periodic sweep do not need building in Phase 2, but they should not be a discovery in Phase 4.

  8. Read Clover's store-hours, blackout and order-type endpoints

    Before designing our own opening-hours logic. Clover already knows all of it.
