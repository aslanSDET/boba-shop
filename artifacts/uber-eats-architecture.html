The Uber Eats seam

Uber Eats has been running against the Snowdaes Clover account this whole time. It is the same integration we are building, by a company with a thousand engineers, and its shape is visible from the outside. This is what it does, how it keeps a menu fresh, and which parts of it we should copy.

Uber never calls Clover

The first thing to get right, because it changes what you look for.

Uber Eats holds no Clover token and issues no request to api.clover.com. Uber talks only to whoever built the connector, and for a Clover merchant that party is Clover itself — the Uber Eats app in the Clover App Market, running on Clover's servers. Uber's own developer documentation is explicit that the POS vendor writes the integration; Uber supplies the API surface and the webhooks.

That is why setup asks for your Clover merchant ID in Uber's POS StoreID field. You are not granting Uber access to Clover. You are telling Uber which store the webhooks belong to, so Clover's connector can route them.

The menu is a snapshot, not a live read

This is the design decision worth internalising, because we made the same one and it is easy to talk yourself out of.

Uber does not query Clover when a customer opens the Snowdaes page. Clover's connector pushes a complete menu to Uber, replacing what was there, and Uber serves its own copy. When Uber wants a fresh one it asks, by firing store.menu_refresh_request at the connector — it still never reaches into Clover itself.

At Uber's traffic a live read per page view would be absurd, so of course they cache. The useful part is that this is not an Uber-scale-only trick: it is the only sane shape, and it is the shape src/lib/clover-hours.ts already uses, where fetchWeek() is the single function that touches Clover and everything downstream works on plain data.

A push model drifts, and we can prove it

Comparing the live Billerica listing against src/config/menu.billerica.generated.ts: 119 items each side, 118 identical prices, zero differences. Same names, same descriptions, same $0.00 bases rendered as "Priced by add-ons".

One exception. Green Apple ($6.45, Fruit Teas) exists in Clover and is absent from Uber Eats. That single row is the whole lesson: a pushed snapshot is only as fresh as the last push, and even a mature connector ends up one item out of step. Any cache we build will do the same thing, and should be designed expecting it rather than hoping otherwise.

Orders arrive as a webhook and become a Clover order

The inbound path is a small state machine rather than a single call. Uber fires orders.notification; the connector acknowledges it, fetches the full order, then explicitly accepts or denies. Only then does it write into Clover. The acknowledge and the accept are separate steps on purpose — the first says "received", the second says "the kitchen has it".

We have no equivalent, and currently need none: an order on our site is created because a card was charged, so there is nothing to accept and nobody to deny to. That asymmetry is worth remembering the day someone asks for order rejection when an item runs out.

Our credential is not their credential

The difference is one line of HTTP, and most of the risk in this build lives inside it.

Clover's connector is an App Market app. A merchant installs it, Clover mints a token scoped to the permissions that app declared, and the merchant can revoke it by uninstalling. One app, thousands of merchants, no shared secret between them.

We do the other thing. src/lib/clover.ts reads a static merchant API token out of the environment and puts it on every platform call, with CLOVER_MERCHANT_ID naming the single shop:

headers.authorization = `Bearer ${required("CLOVER_API_TOKEN")}`;
headers["X-Clover-Merchant-Id"] = merchantId();

For one shop this is the right call — an App Market app would be weeks of OAuth plumbing to serve a single merchant we already have credentials for. But it is not the same security model, and it is worth being precise about what we gave up rather than discovering it later.

Three things we do that Uber's connector has no reason to

guardProductionWrite() refuses any non-GET against production outright, so the proof of concept physically cannot put paper in a working kitchen. optional() makes every secondary call — the print event, for one — incapable of failing a sale that already took money. And the tokenisation key is fetched at request time in exchange for a credential we already hold, rather than pasted into .env.local as a second secret to leak.

None of that is Uber's problem, because Uber is not a side project pointed at a family member's live till. It is the right kind of paranoia for what this actually is.

Guidance

What this should and should not change about the build.

Keep the single Clover seam

src/lib/clover-hours.ts
Already right. Do not erode it.

One function performs I/O and returns plain data; everything else is pure. That is the same separation Clover's connector must have internally, and it is what makes the eventual DynamoDB swap a one-function job. The failure mode is gradual: a Clover call leaking into a component, then another, until the cache is unimplementable.

Cache the menu without apology

src/config/*.generated.ts
Validated by Uber doing exactly this

A generated, committed menu is not a shortcut we took because the database was deferred. It is the same architecture Uber runs, one step less automated. The honest gap is the trigger: Uber gets a refresh webhook, we get a person remembering to re-run a script. Clover publishes inventory webhooks, and wiring one to regenerate the menu is the natural next step — not a rewrite.

Clover stays the calculator

Now four writers on one merchant

The counter, Clover's own ordering page, Uber's connector and our site all create orders against one merchant. Clover is built for that. But it is also the concrete reason not to compute totals ourselves: four writers and one calculator reconcile, four writers and four calculators do not. The numbers in useCart stay a preview.

Do not build the middleware

Deliverect · Otter · Chowly · Cuboh

An industry exists solely to be the box in the middle, because every marketplace times every POS is an N×M problem. Owner.com is native on Clover and Square and routes everything else through Otter. We have one POS, one merchant and one menu we can read end to end — the easiest instance of the problem. Resist any abstraction that pretends otherwise.

Open

  1. Menu refresh trigger. Today the menu is only as fresh as the last manual import-menu.mjs run. Clover inventory webhooks are the fix; nothing else about the design changes.
  2. Popularity. isPopular is false on all 93 items, so the badge is dead. Uber Eats has published eight, ranked. Good enough to seed, but it is the delivery crowd's taste — computing it from Clover sales is the real answer.
  3. Order identity across writers. Four systems now create orders on one merchant. Our pickup code is the last four of the Clover order id, which is fine, but nobody has checked it against a busy Saturday with Uber orders interleaved.
  4. Idempotency on order creation. The one item on this page that is a defect rather than a trade-off. A server-side key on /api/checkout, derived from the cart, would close the hole the useRef only hides.
  5. Authentication before anything is public. Not needed on a laptop, not optional the day a URL exists.
