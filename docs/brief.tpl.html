02

How Clover actually works

Clover is three layers over one database. Once you see that, everything else follows.

Three things worth internalising

  1. The online store is not a separate system. snowdaes-north-billerica.cloveronline.com has no menu of its own. The owner edits an item in the Clover dashboard and the website changes. That is why scripts/fetch-clover.mjs finds a complete structured catalog — it is their inventory.
  2. Every ID we already hold is a real Clover inventory ID. This is the unlock for section 06: we are not scraping a menu, we are holding the keys needed to write orders back in.
  3. Two tax IDs on every single item, at both stores — 119/119 and 124/124, two distinct IDs each. Almost certainly MA state meals tax plus the local option meals tax. Confirm it rather than hard-coding the 8.75% currently mocked in src/store/useCart.ts.
{ "id": "28XHGQDK3TNHM", "name": "Pandan Mango Sticky Rice", "price": 865,
  "modifierGroupIds": ["WCX2453DNC6TR", "PFK8A1CWC1444"],
  "taxIds": ["NHWS2PP5AT8PW", "A16YCATHNY5CY"] }

price is in cents. 28XHGQDK3TNHM is exactly the identifier Clover's Orders API expects. From assets/clover/billerica.json.

Constraint

Clover is processor-locked. The hardware is tied to the processor it was sold through, and rates depend on which reseller sold it — Clover direct, a bank, or an ISO. You cannot swap in your own gateway for the in-store terminal. So "move the shop to Stripe" is not on the table without abandoning their POS, which will not happen.

Why this diagram decides the architecture

  • Staff have one screen they already watch. Any design that adds a second — a tablet showing our orders next to the Station showing theirs — gets ignored during a rush. A missed order is worse than no website.
  • PLAN.md Phase 4 proposes exactly that second screen (/kitchen, tap-to-advance). Right build if we replace Clover; wrong build if they keep it. Do not build it until the owner questions come back.

What Clover's online ordering can't do

The gap that justifies this project is not price, it's capability. 06

The recommendation, in detail

Option B. We own everything above the money; Clover owns the money and the kitchen.

Why each piece

  • Hosted Checkout or iframe, not the raw Ecommerce API. API-only requires independent PCI DSS certification. Hosted Checkout redirects to a Clover-hosted branded page; the iframe tokenises the card in-page and returns a clv_ token. Either keeps us at SAQ-A. Start with Hosted Checkout; move to the iframe later if the redirect hurts conversion.
  • Rewrite Clover's order — do not create a second one. (Revised 28 Aug 2026 after the spike.) Hosted Checkout creates the order and attaches the payment itself, so pushing an atomic order too would mean two orders for one sale. The webhook instead rewrites the order Clover already made: its line items arrive free-form with no item.id, which makes them ineligible for printing, so we swap them for inventory-linked ones with real modifiers. Measured: a locked / PAID order accepts adds and deletes, and its total stays pinned to the payment — the rewrite cannot break the payment match.
  • Merchant-generated API tokens — no app, no approval. The biggest assumed risk in Option B has largely evaporated. Clover's own OAuth FAQ: "For single merchant integrations… you can use a merchant-generated token which allows you to access Clover APIs for that specific merchant without initiating the full OAuth flow." The owner generates both credentials from their own dashboard, behind 2FA. For the record, the fallback is worse than assumed — private apps still require Clover approval before distribution; keep them in reserve for a multi-location rollout.
  • Refunds stay in Clover. The Platform API does not process refunds; the Ecommerce API does for its own payments, and the dashboard always does. Do not build a refund UI.
  • The Clover catalog stays the source of truth. Sync nightly into DynamoDB. The owner keeps editing the menu where they already edit it, and our site follows. This is what makes the system maintainable after we walk away.

The two credentials, and where the owner clicks

CredentialWhere the owner gets itWhat we use it for
Merchant API tokenSettings → Business Operations → API tokens, permissions scoped per endpointRead inventory, create the atomic order, fire the print event
Ecommerce API tokenSettings → Ecommerce → Ecommerce API Tokens, integration type Hosted CheckoutCharging the card

Two caveats, neither blocking. One Clover docs page frames merchant tokens as a sandbox convenience while the OAuth FAQ describes them as fine in production for exactly this case — confirm in writing with Clover developer relations, which is one email, not a six-week unknown. And only one Ecommerce API token exists per merchant account, so if the shop already uses it for something, we share or replace it rather than generating blindly.

Three implementation rules this locks in

  • Fire the ticket explicitly. POST /v3/merchants/{mId}/print_event with the order ID routes to the firing device's order printer and returns a print-event ID. Storing that ID is our proof the kitchen actually saw the order — worth more than any status field we could invent.
  • Push the discount into the Clover order, not just into our arithmetic. If a promo applies and Clover records full price, the shop's books disagree with the deposit every time a code is used.
  • Never lose a paid order. Persist before pushing, retry with backoff, alert on failure. A payment with no ticket is the worst state this system can reach.

07

Provisioning AWS securely

You already made the right first move: a dedicated boba-shop-deploy IAM user scoped to AdministratorAccess-Amplify, kept separate from the machine's existing full-admin credential.

The checklist, in priority order

  1. MFA on the root user, then never log in as root again. Highest-value five minutes in the project.
  2. MFA on boba-shop-deploy, and rotate its access key on a schedule.
  3. A billing budget alarm at ~$50/month. Not security — but a runaway loop is a financial incident, and this is how you find out in hours instead of at month end.
  4. Secrets never in the repo. .gitignore already covers .env* and the .aws redirect footgun; nothing env-shaped is tracked. Clover tokens and webhook signing secrets belong in Amplify secrets / SSM. Anything prefixed NEXT_PUBLIC_ is public — the Clover public key belongs there, the private key never does.
  5. Two environments. Sandbox with Clover test credentials, main with production. A test order must never print in a real kitchen.
  6. Let the schema enforce access. One rule to fix: the sketched Order model allows publicApiKey().to(['create']). A public key that can create orders can create garbage orders — orders should be created only by the Lambda after a verified payment webhook.
  7. CloudTrail on, CloudWatch alarms on Lambda errors and webhook failures.
08

Do you need a CDN?

Yes — and you don't buy one separately. Amplify Hosting is CloudFront underneath. Deploying gives you the CDN, TLS termination and edge caching in one step. The S3 + CloudFront path is the same infrastructure with more wiring by hand.

Cost: the free tier covers 5 GB stored on CDN and 15 GB/month transfer out; beyond that it's $0.15/GB served and $0.023/GB-month stored, with build minutes at $0.01 and 1,000 free. For a two-location boba shop, images dominate and transfer lands in single-digit GB — call it $0–5/month.

The real reason isn't cost, it's phones. Almost all traffic is cellular, mid-range Android, standing outside the shop. A CDN turns a cross-country round trip into a nearby one on every image. Pair it with what's already in the repo: .avif assets, Next's <Image>, and long cache headers on menu images that never change.

Resolves an open decision

Amplify Hosting settles the hosting question in PLAN.md §9. It is CloudFront, it matches the Amplify Gen 2 backend already chosen, and it keeps everything in one AWS account for the franchise-handover story. Vercel is fine engineering and a worse fit for a pitch headlined "enterprise-grade AWS".

09

Security, ranked by what will actually happen

Not a generic checklist. Ordered by real probability for a small merchant taking card payments.

Never trust a number that came from a browser.

The cart in src/store/useCart.ts computes a subtotal for display. At checkout the server re-reads every item and modifier price from its own catalog copy, re-applies the promo code, recomputes tax, and charges that. If the client's total disagrees, the client is wrong. Without this, curl buys a Thai Dye for a penny.

Never touch a card number.

Hosted Checkout or the tokenising iframe means the card number never reaches our servers or our logs. That is the difference between PCI SAQ-A — a self-assessment questionnaire — and an audit.

Notes on the rest

  • Promo codes are the realistic loss vector. Not hackers — Reddit. A code meant for one campaign is on a coupon aggregator by Thursday. Design for it: single-use codes tied to a customer, hard expiry, minimum spend, one campaign per order, and a redemption counter enforced in a conditional DynamoDB write so two simultaneous requests can't both win.
  • PLAN.md proposes "a simple shared passcode" for /kitchen. Shared passcodes leak to former employees and never get rotated. If a staff view exists at all, put it behind the same auth provider with a role claim.
  • WAF is worth ~$15/month once real money flows — $5 per web ACL, $1 per rule, $0.60 per million requests. Managed common rule set plus one rate-based rule. Not needed pre-launch.
  • You'll now hold PII you don't hold today — phones, emails, order history. Publish a privacy policy, keep PII out of logs, give customers a way to be deleted. Massachusetts has its own breach-notification statute; keeping card data entirely out of scope removes most of the exposure, and the remainder is worth thirty minutes of a lawyer's time before launch.

Revised phasing

The reordering that matters

Real menu data moves from Phase 6 to Phase 2. Building auth and payments against 24 invented items when 119 real ones with real Clover IDs are sitting in assets/clover/ is wasted motion — and that real catalog is exactly what the order push in Phase 4 depends on.

14

Questions for the owner

Bring these to one meeting. A, B and D are blocking — the architecture cannot be chosen without them. Ask for a statement or a screenshot rather than a recollection wherever money or configuration is involved.

A · Clover account & contract

Blocking
  1. Who sold you Clover — Clover directly, your bank, or a reseller? Who do you call when it breaks?
  2. Can I see one recent monthly statement? Specifically: plan and fee per device, card-present rate, card-not-present rate, monthly minimum, PCI compliance fee, gateway fee.
  3. Which Clover plan, and how many devices at each location?
  4. When does the contract end, and is there an early-termination fee?
  5. Does your agreement restrict where else you can take online orders?
  6. Is Billerica one merchant account or two? Same legal entity?
  7. Can you generate API tokens in your dashboard? Settings → Business Operations → API tokens. Needs 2FA switched on first.
  8. Is anything already using your Ecommerce API token? There is only one per merchant account — we must not overwrite a working integration.

B · How orders reach you today

Blocking
  1. Walk me through what happens when an online order comes in. Does the Station beep? Does someone have to be watching it?
  2. Does a kitchen ticket print automatically, or does staff press print?
  3. Is there a printer in the back, or does everything print at the counter? Any kitchen display screen?
  4. Do you accept each order and set a prep time, or does it just appear?
  5. Does the customer get a text when it's ready?
  6. Roughly how many online orders a day vs. walk-ins? When's the rush?
  7. What goes wrong today? Missed orders, wrong modifiers, pickup-time complaints, printer jams?
  8. If a new website sent orders to that same printer, would that be better or worse than what you have?

C · Aggregators

  1. Are you on DoorDash, Uber Eats or Grubhub? What commission do they take?
  2. What share of your orders comes through them?
  3. Are your prices higher on those apps than in store?
  4. If you could move those customers to your own site, would you want to?
